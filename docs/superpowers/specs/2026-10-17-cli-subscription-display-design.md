# CLI Web 首页订阅额度卡片

状态：已完成 builder check，用户已确认，实施完成。分支：`feat/cli/subscription-display`（从本地 `main` 创建）。审阅结果：无影响规划的重要遗漏。

## 意图与已确认需求

用户希望 CLI Web 首页展示与桌面端首页相同的各渠道额度、订阅套餐卡片；关闭本项目桌面端后，CLI 仍能独立获取订阅数据。无需启动 Electron，也不是读取桌面端留下的额度快照。

成功标准：同一台机器、同一供应商账户及相同数据条件下，CLI 与 Desktop 展示相同的套餐、额度窗口、剩余比例、重置时间和详情。

## 范围

- 覆盖桌面端当前网格中的 12 个渠道：Codex、Claude、Cursor、GitHub Copilot、Grok、Kimi、ZCode、Antigravity、Qoder、MiniMax、OpenCode、DeepSeek。
- 沿用桌面端首页位置：概览指标下方、热力图上方；沿用卡片样式、排序、响应式布局及详情展开行为，不重新设计 UI。
- 沿用自动识别规则：没有可展示额度的渠道不占位；缺少登录状态不展示虚假的额度。
- 沿用首次加载、窗口重新获得焦点、单卡手动刷新的行为，以及各读取器已有缓存、并发合并和失败降级语义。
- 补齐 CLI 面板的订阅渠道显示开关，与桌面端默认全部开启的行为一致。偏好保存在各自 renderer 的 localStorage，不承诺跨端自动同步。

以下为实现方提出、待随本设计确认的边界：只覆盖 CLI 托管面板及 `VITE_API_TARGET=cli` 开发模式；线上掘金 Web（server 模式）不展示订阅卡片，不读取本地凭据、不请求 CLI 订阅接口。不新增渠道、不新增登录或授权流程，不上传订阅数据到云端。

## 独立运行的含义

CLI 直接复用本机供应商的现有认证与数据来源，独立于本项目 Electron 应用。某些上游读取器本身依赖供应商工具的本地服务或进程，保留这些必要条件；关闭本项目桌面端不影响读取，并不承诺关闭所有供应商工具后每个渠道仍有实时数据。

CLI 的订阅读取不改变既有 CLI/Desktop runtime owner、采集、同步及上传互斥规则，也不要求 CLI 成为采集 owner 才能读取订阅。

## 代码与数据架构

实现方选择：把订阅类型、mapper、读取器及其必要的纯 Node 辅助模块提取到 `packages/core` 的独立订阅模块；Desktop IPC 和 CLI local-api 共同调用它，避免维护两套凭据解析和供应商协议。Desktop 保持原 IPC 方法和返回值契约，必要时原文件保留轻量转发导出以降低迁移风险。

核心模块不依赖 Electron。现有 `subscription-fetch.ts` 使用 Electron `net.fetch`，提取时采用可注入的请求函数：CLI 默认使用 Node 请求实现；Desktop 注入原 Chromium 请求实现，保留系统代理/PAC 行为。不得宣称 Node 自动具备 Chromium 的代理能力。

Node 兼容性：仓库声明 Node >=20，而 Cursor、Copilot 等读取器目前静态导入 `node:sqlite`。保持现有最低 Node 版本，优先复用 core 已有 `parsers/sqlite.ts` 的运行时探测及 `sqlite3` CLI 回退能力，不引入新的原生数据库依赖。Node 20 上数据库渠道沿用项目现有的 sqlite3 安装条件；缺少能力时仅该渠道失败，并给出可理解的诊断，不能因静态导入使整个 CLI 启动失败。实施时核对读取器是否需要扩展现有 helper 的只读查询能力。

Dashboard 与 Desktop renderer 是同构但独立的代码。复用现有卡片及其展示辅助函数，在各自数据访问层适配 HTTP 和 IPC；不在浏览器伪造 `window.tud`，不让 Dashboard 直接依赖 Desktop 主进程源码。同步修改同名 UI 副本，并让订阅展示数据和类型引用 core 的明确子路径导出，避免浏览器打包 Node 模块。

## 本地 API 契约

建议新增 `GET /functions/tud-subscription/:channel`，`forceRefresh=1` 表示手动强制刷新。各渠道独立请求、独立返回，不等待最慢渠道后才显示全部卡片。

- 使用现有 `{ success, message, data }` 响应封装；`data` 是对应渠道的脱敏 snapshot，保留现有字段和状态语义。
- 只允许固定渠道 ID；未知渠道返回 404 和稳定错误码，不拼接文件路径或导入路径。
- 上游未登录、未安装、暂不可用等是 snapshot 的业务状态；意外内部错误返回通用错误，不暴露原始异常、凭据、认证文件路径或上游响应。
- `forceRefresh` 只绕过已有成功缓存，继续共享进行中的请求并遵守已有超时策略。
- 复用并核对 local-api 的回环监听与浏览器来源限制；新增敏感本地读取端点只接受本地面板来源和项目 CLI 开发来源，不能因现有通用 CORS 配置而让任意网页读取账户额度。具体来源判定与开发端口以现有 CLI 配置为准。

凭据只在 Node/Electron 后台读取并用于原有可信接口，不传给浏览器、不写入日志、不修改供应商认证文件。缓存仍由读取器管理，不建立新的跨端磁盘缓存或后台常驻轮询任务。

## 失败行为

单渠道失败不影响首页用量、其他渠道或 CLI 启动。保留已有 stale 结果与展示规则，不将请求失败变成 100% 剩余，不编造未知套餐和重置时间。读取过程不阻塞首页基础数据加载。

## 验收与验证

1. 不启动本项目 Desktop 时启动 CLI，准备有效本地账户的渠道能显示套餐和额度；由 CLI 后台发起读取。
2. 卡片位置、剩余比例、额度分组、刷新/到期时间和详情与桌面端一致；没有额度的渠道不占位。
3. 各渠道分别刷新；窗口聚焦沿用缓存；并发请求合并、失败后的 stale 结果符合原有读取器语义。
4. 渠道开关持久化，关闭后不挂载/请求对应卡片；线上 server 模式不发起订阅读取。
5. HTTP 接口覆盖合法/未知渠道、刷新参数、业务失败、意外异常脱敏和来源校验；使用虚拟认证材料与 mock 上游，不使用真实账户做自动化测试。
6. 迁移后的 mapper、读取器及相关已有测试通过；Desktop IPC 契约与代理注入不回归。
7. 验证 Node 20 的 CLI 启动及 SQLite 渠道读取，验证当前开发 Node 的构建与测试。运行 `pnpm build`、Desktop typecheck、四个包的测试；新增用户可见变更的 changeset。

## 留给实现方的选择

模块拆分、依赖注入接口、SQLite 兼容实现、测试夹具与精确测试命令由实现方决定并记录在后续计划中。无需为了这次需求统一所有供应商 snapshot 形态，或调整原有额度算法。浏览器操作遵循项目约定，未经用户要求不自动使用 agent browser。
